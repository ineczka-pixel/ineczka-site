# add-feature — новая функция на сайте Ineczka

Полное описание цикла: `docs/workflow/adding-a-feature.md`. Отвечай автору по-русски, простыми словами.

## 0. Прочитать (обязательно, до любых правок)
1. `CLAUDE.md`.
2. Файлы фич, которые задача затрагивает (`docs/features/README.md` → нужные файлы) — там номера строк, образцы блоков и тесты.
3. `docs/known-issues.md` — не наступить на известное и не «починить» случайно без спроса.
4. `grep -ril "<ключевые слова>" docs/solutions/` — прочитать найденные уроки.
5. `docs/design-system.md`, если меняется внешний вид.

## 1. Обсудить (только если неясно)
Не больше 2–3 вопросов через AskUserQuestion: что увидит посетитель, есть ли материалы (картинки/тексты), важен ли телефон.
Если ответ очевиден из контекста — не спрашивать, а записать допущение в план.

## 2. План
- Мелочь (текст, одна ссылка, замена картинки): план из 3 пунктов в чате.
- Иначе: `docs/plans/YYYY-MM-DD-<slug>.md` по `docs/plans/_template.md` (формат ralphex). >3 независимых задач — предложить автору запуск через ralphex (`docs/workflow/ralphex.md`).

## 3. Тесты сначала
- Новое поведение → сценарий в `tests/e2e/<фича>.spec.ts` (или новый spec со ссылкой на файл фичи в первой строке). Используй `openSite` из `tests/helpers/site.ts`, локаторы по роли/тексту/aria-label.
- Новый блок/вид → если нужен новый скриншот, добавить его в `tests/review/capture.spec.ts`; вопрос к человеку → объект в `docs/testing/human-checklist.json` (`id`, `area`, `title`, `how`, `why`, `shots`).
- Убедиться, что новый тест падает по правильной причине: `npx playwright test -g "<название>" --project=e2e-desktop`.

## 4. Реализация
- Правки только в `index.html`/`assets/`. Копировать ближайший похожий блок; inline-стили; цвета из дизайн-системы; JS ES5 глобальными функциями.
- Каждая картинка — `alt`, каждая кликабельная работа — `button.gallery-btn` с `aria-label`.
- Проверить 375px: у новых сеток `auto-fit/minmax` или перенос, не фиксированные колонки.

## 5. Проверка
`npm run verify`.
- e2e должны быть зелёными. Нельзя удалять/ослаблять тесты. Чужой найденный баг → `test.fail(true, 'KI-xxx: …')` + запись в known-issues + сказать автору.
- Если визуальные эталоны упали **из-за намеренного изменения** — это ожидаемо; НЕ обновлять до одобрения.
- Упало что-то другое — чинить, повторять.

## 6. Самопроверка diff
`git diff` глазами строгого ревьюера: не задеты ли соседние блоки, адаптив, доступность, лишний код, соответствие файлу фичи. По желанию — `/code-review`.

## 7. Показать человеку
- Опубликовать `review/index.html` через инструмент Artifact (icon `checklist`) и дать автору ссылку.
- В ответе: что сделано (2–4 пункта), что проверил робот (цифры), **что именно посмотреть глазами** (id HR-xxx), что осталось неясным.
- После «ок» от автора: `npm run test:visual:update`, закоммитить эталоны.

## 8. Compound (не пропускать)
- Было что-то неочевидное → `docs/solutions/YYYY-MM-DD-<slug>.md` по шаблону + строка в `docs/solutions/README.md`.
- Обновить `docs/features/<фича>.md` (строки, «Как изменить», «История»); новая фича → новый файл по `_template.md` + строки в `docs/features/README.md` и таблице `CLAUDE.md`.
- Сдвинулись номера строк → обновить их в CLAUDE.md и файлах фич.
- `docs/known-issues.md` — отметить исправленное, снять `test.fail`.
- План → `docs/plans/completed/`.
- Коммит(ы) и push в рабочую ветку.
